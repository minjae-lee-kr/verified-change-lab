# Verified Change Lab

**검사를 통과한 코드와 실제로 반영한 코드가 같다는 것을 어떻게 확인할까?**

[English](README.md)

자동화에서 발생할 수 있는 작은 실수를 실제로 재현한 실험입니다. 변경을 검사하고 승인을 기다린 뒤, 그때의 작업 폴더를 커밋하면 중간 수정 때문에 검사한 코드와 반영한 코드가 달라질 수 있습니다. 이 실험의 잘못된 경로는 격리된 가상 Git 저장소에 미검증 코드를 실제 반영하고, 이후 런타임 검사에서 실패합니다. 보호된 경로는 작업 폴더가 바뀌어도 검사한 불변 커밋만 선택합니다.

실제 Git 객체, 별도 Node 검사 프로세스, TypeScript 컴파일러, 동시에 실행되는 변경 프로세스, CAS 이후 프로세스 강제 종료를 사용합니다. LLM이나 외부 서비스는 호출하지 않습니다. 재시도 정책 코드는 독립 제작한 실험용 예제이며 회사 구현이나 실무용 재시도 라이브러리가 아닙니다.

## 실행

Node 24.12–24.x, Git, pnpm 11이 필요합니다. 설치 이후 네트워크나 자격 증명은 필요하지 않습니다.

```sh
pnpm install --frozen-lockfile
pnpm check
pnpm experiment
pnpm serve
```

**http://127.0.0.1:4318**에서 실제 실행으로 생성한 보고서를 봅니다. 한국어 브라우저에서는 한국어가 기본이며, 언어를 바꿔도 선택한 사례와 펼친 근거는 유지됩니다. 원시 명령과 검사 결과는 `.lab/`, 경로를 정리한 전체 보고서는 `dist/report.json`에 남습니다. 소스 지문, 실행 환경, Git 커밋 및 작업 폴더 변경 여부를 함께 기록합니다.

Git 변경 대상은 이 프로젝트의 `.lab/`에 새로 만드는 가상 저장소뿐이며, 경로를 정리한 보고서는 `dist/`에 씁니다. 사용자 저장소를 받는 옵션, 원격 저장소, 배포 동작은 없습니다. 비어 있는 Git 템플릿과 격리된 전역·시스템 설정으로 fixture를 초기화합니다.

## 직접 확인하는 다섯 가지 상황

| 상황              | 오류 주입                                               | 관찰 결과                                                                                               |
| ----------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 검사 후 코드 변경 | 검사 이후 수정된 작업 폴더를 커밋                       | 잘못된 경로는 미검증 코드 반영 후 검사 실패. 보호된 경로는 검사한 커밋 유지.                            |
| 검증의 의미       | 빈 검사 결과 또는 후보의 `strict`와 `noCheck` 동시 설정 | 후보 설정을 따른 컴파일러는 통과하지만 독립 정책은 오류를 발견. 누락되거나 약화된 근거로 승인하지 못함. |
| 근거 재사용       | A의 근거로 다른 커밋 B 승인 시도                        | 커밋 불일치로 거절. 별도로 주입한 논리 시각에서는 만료 경계도 거절.                                     |
| 동시 승인 경쟁    | 두 프로세스가 같은 기준에서 다른 후보로 변경            | Git의 조건부 갱신은 하나만 성공. 재조회에서는 선택된 후보와 충돌이 하나씩 관찰됨.                       |
| 응답 전 종료      | CAS 이후 응답 파일 생성 전에 실제 프로세스 종료         | 호출자는 응답을 받지 못함. ref 재조회로 후보가 선택된 현재 상태 확인. 이전 기준으로 재요청하면 거절.    |

보고서의 승인은 스크립트가 수행하며 실행 기록에도 그렇게 표시합니다. 만료 실험은 시간을 주입한 경계 검사이며 실제 5분을 기다린 것으로 표현하지 않습니다. 나머지 프로세스 및 Git 효과는 실제 로컬 I/O입니다.

## 사람이 직접 승인하는 흐름

```sh
pnpm lab prepare
```

변경 diff, 커밋, 필수 검사, 근거 digest, `review.json`을 확인합니다. 출력된 정확한 확인 명령을 실행하고, 반영은 별도 명령으로 수행합니다.

```text
pnpm lab approve <생성된-fixture-id> <후보-커밋> <근거-digest>
pnpm lab apply <생성된-fixture-id>
pnpm lab reconcile <생성된-fixture-id>
```

확인 값이 다르면 승인을 거절합니다. 검증 시작 5분 후 근거가 만료되므로 오래 지났다면 새 fixture를 준비합니다. 승인 명령은 로컬 결정만 기록하고, 반영 명령은 해당 bare 저장소의 `refs/heads/release`만 변경합니다. 표시된 검토자 이름은 사용자 인증이 아닙니다.

## 근거의 연결

불변 후보 커밋 → 검사별 독립 스냅샷 → 완전하고 신선한 검사 결과 → 기준 커밋·후보·근거 digest에 연결한 승인 → 실제 ref의 이전 값이 일치할 때만 변경합니다.

승인 계층은 `src/policy.ts`에서 필수 검사 목록을 독립적으로 읽습니다. 검사기가 반환한 목록으로 필요한 검사 범위를 정하지 않습니다. 검사 ID, 호출 nonce, 커밋·트리·정책, 시간 범위, 구체적인 검사 성공과 프로세스 종료 상태를 모두 확인합니다. 빈 결과, 일부 누락, 중복으로는 승인할 수 없습니다.

strict 컴파일 옵션과 검사할 소스 목록도 후보의 `tsconfig.json`이 아닌 신뢰하는 검사기 정책에 둡니다. 독립 리뷰에서 후보가 `strict: false`로 검사를 완화하는 우회가 재현됐고, 현재 회귀 테스트는 설정 완화와 빈 파일 목록으로도 필수 검사를 생략할 수 없음을 확인합니다. `apply … --dry-run`처럼 오해할 수 있는 미지원 인자도 실제 변경 전에 거절합니다.

보고서에서는 같은 implicit-any 소스가 후보 설정 `strict: true, noCheck: true`를 따른 실제 컴파일러에서는 통과하지만, 독립 정책의 검사기에서는 실패하는 것을 비교합니다. 검사 이름과 존재 여부만으로는 실제 검사 의미까지 알 수 없다는 반례입니다. 보고서 생성 시작과 끝의 소스 지문이 달라지면 해당 실행에 정확한 소스 증명을 붙일 수 없으므로 생성을 중단합니다.

정책 digest에는 검사기·실행기·승인 로직·CLI의 소스, 필수 검사 목록, 패키지·lockfile, Node/TypeScript 버전이 포함됩니다. 후보 코드와 검사 정책은 별도 대상입니다. 설치된 의존성 파일 전체나 Node 바이너리까지 검증한 것은 아닙니다.

검사 프로세스는 5초 제한과 합계 32 KB 출력 제한을 사용합니다. 종료할 때 자신이 만든 프로세스 그룹 또는 Windows `taskkill /T /F`를 사용하며, 실제 자식 프로세스의 heartbeat가 멈추는 테스트로 확인합니다. 이는 우발적인 멈춤을 제한하는 장치이며 악성 코드용 격리가 아닙니다.

기록은 직접 실행한 프로세스의 종료 확인과 프로세스 트리 종료 요청의 수락 여부를 구분합니다. 정상 종료에서는 후자가 `null`이며 모든 하위 프로세스가 없다는 뜻이 아닙니다. 트리 종료 요청의 수락도 그룹을 벗어난 프로세스까지 증명하지 않습니다. 이 고정 검사기는 하위 명령을 만들지 않으며, 범용 실행기로 확장하려면 job object나 샌드박스 같은 운영체제 격리가 필요합니다.

## 한계도 실험 결과에 포함합니다

**현재 값 비교는 일회용 실행 권한이 아닙니다.** 부정 증명 테스트는 기준 → 후보 → 기준으로 ref를 되돌린 뒤 아직 만료되지 않은 승인을 재사용합니다. CAS는 다시 성공합니다. 이 A-B-A 사례가 있으므로 단순 재요청 거절을 승인 토큰 소모나 정확히 한 번 실행 보장으로 해석할 수 없습니다. 그런 성질에는 포인터 비교 외에 영속적인 작업 식별자와 이력이 필요합니다.

응답 유실 뒤 후보 ref가 관찰돼도 다른 작성자가 변경했을 수 있습니다. 기준 ref가 관찰돼도 과거에 아무 일도 없었다는 뜻은 아닙니다. 따라서 재조회는 현재 후보·기준·다른 커밋 중 무엇을 봤는지만 기록하며, 변경 주체를 추정하거나 충돌한 값을 덮어쓰지 않습니다.

- 로컬 소스와 프로세스를 신뢰합니다. 해시는 서명이 아니며 로컬 파일 작성자가 근거·승인·기록을 위조할 수 있습니다. 실행 전후 해시는 악의적인 중간 수정 후 원복을 탐지하지 못합니다.
- 예제 코드는 사용자 프로세스 권한으로 실행합니다. 샌드박스가 아니므로 외부의 신뢰할 수 없는 코드를 실행하는 도구로 바로 확장하면 안 됩니다.
- 성공한 CAS는 로컬 ref 하나만 변경합니다. 배포, 작업 폴더 변경, 외부 서비스 실행을 증명하지 않습니다. 실험에서 수정된 작업 폴더는 그대로 남습니다.
- 만료는 로컬 시계를 사용합니다. 시계 역행, 여러 호스트의 신뢰, 디스크 fsync 수준 내구성, ref 삭제나 악의적인 symbolic-ref 변경은 실험 범위 밖입니다.
- 작은 런타임 계약과 strict 컴파일 검사는 선언한 예제 범위만 확인합니다. 일반적인 정확성, 실서비스 적용, 처리 규모 또는 모델 성능을 주장하지 않습니다.

의도적인 설계 선택은 승인 대기 동안 변경될 수 있는 작업 폴더를 다시 읽는 대신 불변 후보를 준비해 산출물의 동일성을 유지하는 것입니다. 추가 객체·스냅샷 저장과 코드 또는 정책 변경 시 재검증 비용이 생깁니다. 모든 실행 문제를 해결하지는 않지만, 이 실패는 구체적으로 드러내고 재현할 수 있습니다.
