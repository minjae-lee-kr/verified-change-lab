# 변경 옆에 영수증을 둘까, 선택한 상태 안에 넣을까?

[English](state-envelope.md) · [기존 실험](../README.ko.md)

기존 실험은 코드 ref를 조건부로 갱신합니다. 응답을 잃은 뒤 ref를 읽으면 지금
선택된 코드는 알 수 있습니다. 하지만 승인이 한 번 사용됐는지는 알 수 없습니다.
다른 작성자가 ref를 이전 값으로 돌리면, 아직 유효한 같은 승인이 다시 조건을
만족할 수 있습니다.

이 별도 실험은 저장 방식을 바꿉니다. 불변 Git commit 하나에 선택한 코드 OID와
실행 영수증을 넣고, ref 하나로 그 상태를 선택합니다. 같은 승인으로 재시도할 때
새 식별자를 만들지 않도록 승인 전체의 digest를 operation ID로 씁니다.
새 선택에는 기존 실제 검사와 승인 내용의 일치 확인이 필요합니다. 검토자의
신원을 인증하는 기능은 아닙니다.

## 고정된 순서로 실행하기

저장소 루트에서 기존 안내대로 의존성을 고정 설치한 뒤 실행합니다.

```sh
pnpm state:experiment
```

매번 새 `.lab/state-envelope-runs/<run-id>/report.json` 경로를 출력합니다.
`dist/report.json`이나 이전 기록을 덮어쓰지 않습니다. JSON에는 실제 Git 명령,
검사 출력, IPC 단계, 관측한 프로세스 종료, 상태 OID와 소스 지문이 담깁니다.
실행 오류, 누락된 사례, 예상과 다른 관측이 있으면 명령은 실패합니다.
미커밋 소스 실행은 그렇게 표시하며, 새 실행을 과거 공개 기록으로 취급하지 않습니다.

별도의 [기록 검사기](../src/state-envelope-check.ts)는 상태, 영수증, 작업자 단계와
종료 관측에서 고정된 사례의 결론을 다시 확인합니다. 상태 본문·OID·부모 목록을
성공한 `git show` 출력과 연결하고, CAS 인자와 코드를 보존하는 candidate ref도
대조합니다. 실행기가 남긴 통과 표시만 믿지 않습니다. 신뢰하는 로컬 기록의 내부
일관성 검사이며, 서명된 증명이나 가능한 모든 Git 이력의 재구성은 아닙니다.
재시도 뒤 마지막 ref 조회와 나중에 수행한 이전 OID 재조회에는 각각 관측 표시를
남깁니다. 표시 바로 앞의 실제 Git 읽기와 순서를 확인하므로, 앞선 조회를 나중
관측의 근거로 대신 쓸 수 없습니다.

확인하려는 차이는 다음과 같습니다.

| 중단하거나 바꾸는 지점                                     | 작업자 종료 뒤 읽은 선택과 영수증                                                  |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 코드 ref 갱신 뒤, 별도 영수증을 쓰기 전에 중단             | 후보는 선택됐지만 영수증은 없습니다. 정상 진행 경로에서는 영수증이 기록됩니다.     |
| 상태 객체를 만든 뒤, state ref의 CAS 전에 중단             | 이전 선택과 이전 영수증이 유지됩니다. 준비된 객체가 존재해도 선택된 것은 아닙니다. |
| Git이 state CAS를 완료한 뒤, 호출자에게 응답하기 전에 중단 | 같은 상태 OID에서 후보와 영수증을 함께 읽습니다. 호출자 응답은 없습니다.           |
| 영수증을 유지한 새 상태에서 이전 코드를 선택               | 같은 승인이 이미 기록되어 있어 새 전환을 하지 않습니다.                            |
| state ref 자체를 최초 commit으로 되감기                    | 보존하던 기록이 사라집니다. 같은 승인이 아직 유효하면 다시 실행할 수 있습니다.     |

부모 프로세스는 IPC 단계에서 실제 Node 작업자를 종료하고, 종료 관측을 기다립니다.
이 단계는 완료된 Git 명령 사이에 있습니다. Git의 rename 도중 중단이나 정전은
재현하지 않습니다. 제한 시간은 실패 상한일 뿐 실행 순서를 정하는 데 쓰지 않습니다.
별도 쓰기 대조군에도 실제로 영수증을 쓰고 정상 종료하는 경로가 있습니다.

## 읽는 쪽의 약속도 달라집니다

state ref를 한 번 읽고, 그 불변 OID를 통해 **두 필드를 모두** 읽어야 합니다.

```text
state ref ──한 번 읽기──> state commit
                          ├─ selectedCandidate: 코드 OID
                          └─ receipts: 승인 digest → 기록된 선택
```

읽기 대조군은 최초 상태를 확보한 뒤 작성자가 후보를 선택하게 하고, 다시 읽습니다.
처음 읽은 선택 값에 ref를 새로 읽어 얻은 영수증을 붙이면 서로 다른 버전이 섞입니다.
처음 확보한 OID로 다시 읽으면 원래 쌍이 유지됩니다. 두 버전을 실제로 읽은
관측이며, 모든 동시 실행의 선형성을 증명한 것은 아닙니다.

## 기존 경로에 바로 붙일 수 없는 이유

- **ref가 가리키는 것이 메타데이터로 바뀝니다.** 코드 commit을 기대하는 배포 도구는
  그대로 쓸 수 없습니다. 한 단계 더 읽어야 하고, 두 필드가 같은 OID를 써야 합니다.
- **새 전환 코드도 승인 정책에 포함됩니다.** 상태 프로토콜과 작업자를 공용 정책의
  지문에 넣습니다. 둘 중 하나를 바꾸면 기존 코드 ref 경로의 승인도 무효가 됩니다.
  정책을 공유해 보수적으로 묶는 비용입니다. 준비 뒤 근거의 유효 시간을 다시
  확인하지만, 그 시각 검사와 Git CAS가 원자적으로 실행되는 것은 아닙니다.
- **기록 보존도 계약에 포함됩니다.** 참여하는 작성자는 영수증을 유지해야 합니다.
  준비한 전환의 유일한 부모는 예상한 직전 상태여야 합니다.
  이 예제는 16개까지만 허용하고 삭제 정책은 구현하지 않습니다. 영수증을 포함한
  상태를 다시 쓰는 비용이 들고, 모든 작성자가 한 ref에서 경합합니다. 처리량은 측정하지 않았습니다.
- **코드 객체도 보존해야 합니다.** 생성한 candidate ref가 코드 객체를 유지합니다.
  JSON에 적힌 OID 문자열만으로 Git의 가비지 컬렉션에서 객체가 보존되지는 않습니다.
- **로컬 작성자는 여전히 이력을 바꿀 수 있습니다.** 해시가 ref 되감기나 객체 위조를
  막지는 않습니다. 부정 대조군은 의도적으로 상태 전체를 되감습니다.

코드를 배포하거나 외부 효과를 발생시키는 실험이 아닙니다. 운영 환경의 정확히
한 번 실행, 수행자 증명, 정전 복구나 임의 작성자에 대한 정책도 입증하지 않습니다.
기존 다섯 사례의 보고서는 별도로 유지합니다.

## 설계 판단에 참고한 자료

- [FoundationDB의 결과 불명 처리](https://apple.github.io/foundationdb/developer-guide.html#transactions-with-unknown-results)는
  재시도와 보존한 완료 기록을 구분합니다. 뒤의 오류 처리 설명은 종료된 결과 불명과
  아직 처리 중일 수 있는 취소도 구분합니다. 여기서는 데이터베이스 보장 대신 실제 작업자 종료를 관측합니다.
- [TigerBeetle의 안정적인 요청 제출](https://docs.tigerbeetle.com/coding/reliable-transaction-submission/)은
  재시도에도 같은 식별자를 쓰도록 합니다. 승인 digest에 이 원칙을 적용했지만,
  금융 시스템의 보장이 이 로컬 예제로 옮겨오는 것은 아닙니다.
- [Jepsen의 선형성 모델](https://jepsen.io/consistency/models/linearizable)은
  관측 대상과 연산 순서를 분명히 합니다. 여기서 대상은 state ref 하나이며,
  코드 ref·영수증·배포·외부 효과를 합친 전체 시스템이 아닙니다.
- [Git update-ref 문서](https://git-scm.com/docs/git-update-ref)는
  이전 값 조건과 여러 ref를 동시에 읽을 때의 한계를 설명합니다.
  이 실험은 연결된 필드를 하나의 불변 상태 객체에서 읽도록 바꿉니다.

실제 순서는 [`src/state-envelope-experiment.ts`](../src/state-envelope-experiment.ts)에서 볼 수 있습니다.
