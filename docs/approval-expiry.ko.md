# 확인할 때는 유효했던 승인, 반영할 때도 유효할까?

[English](approval-expiry.md) · [승인 사용 기록 실험](state-envelope.ko.md)

마지막 유효기간 검사에서는 통과한 승인이 Git에서 변경을 선택할 때는 만료될 수
있습니다. 준비를 마친 뒤 다시 검사하면 그 간격은 줄어듭니다. 하지만 시각 조건이
ref 트랜잭션 안으로 들어가는 것은 아닙니다.

이 실험은 기존 state worker와 실제 Git 명령을 두 번 실행합니다. 승인 기한,
검증 근거, 전환 정책은 바꾸지 않습니다. worker의 `Date.now`만 제어한 논리 시계를
사용합니다. 부모 프로세스와 Git의 시계는 그대로이며, 실제로 5분을 기다리지 않습니다.

| 제어한 순서                                                                                           | worker의 마지막 검사 | 관측한 로컬 결과                                                |
| ----------------------------------------------------------------------------------------------------- | -------------------- | --------------------------------------------------------------- |
| worker의 준비 완료 지점에서 시계를 만료 뒤로 옮긴 후 진행                                             | 만료 후              | 유효기간 검사에서 거절. 초기 ref와 빈 승인 사용 기록 유지       |
| 검사를 통과시킨 뒤 Git의 `reference-transaction` hook을 `prepared` 단계에서 중지. 시계를 옮긴 후 진행 | 만료 전              | 논리 시각상 만료 뒤 ref 반영. 선택된 상태에 승인 사용 기록 보존 |

두 번째 대조에서는 Git이 멈춰 있는 동안 부모가 이전 ref를 직접 읽습니다.
hook은 반환 직전과 Git의 `committed` 단계에서 만료된 논리 시각을 관측합니다.
worker의 완료 응답과 새로 읽은 ref·상태도 일치합니다. 제한 시간은 실패를 끝내는
상한일 뿐, 순서를 맞추기 위한 대기 시간이 아닙니다.

## 실행과 근거 확인

README의 Node·Git·pnpm 요건을 갖춘 뒤 저장소 루트에서 실행합니다.

```sh
pnpm install --frozen-lockfile
pnpm expiry:experiment
node --test test/approval-expiry.test.ts
```

명령은 인자를 받지 않습니다. 새 가상 저장소와 보고서를
`.lab/approval-expiry-runs/<run-id>/report.json`에 만들고 이전 실행은 보존합니다.
보고서에는 소스 커밋, 작업 폴더의 변경 여부, 파일 해시, Node·Git 버전과 두 시계의
구분이 남습니다. 크기를 제한해 수집한 명령 기록에서 로컬 경로는 `<project>`로
표시합니다. 이 표시 문자열은 편집하지 않은 터미널 원본 바이트가 아닙니다.

[`check.ts`](../experiments/approval-expiry/check.ts)는 worker의 시계 조회, IPC 단계,
hook 트랜잭션, 특정 시점에 묶인 Git 조회, 프로세스 결과와 승인 사용 기록으로 각
대조의 결론을 계산합니다. 생성기가 쓴 `passed` 값에 의존하지 않습니다. 테스트는
두 대조를 실제 실행하고, 시각 변경·barrier 누락·ref나 승인 사용 기록 불일치·
프로세스 실패를 거절합니다. 근거 누락, 결과 불명과 시간 초과는 실험 실패입니다.
서명 없는 로컬 기록의 내부 일관성을 확인하며, 실행 주체나 기록의 진위를 인증하지는
않습니다.

## 이 차이에서 결정해야 할 것

‘유효할 때 시작해도 된다’와 ‘만료 전에 반영돼야 한다’는 다른 계약입니다.
`update-ref` 직전에 한 번 더 검사해도 간격은 남습니다. 엄격한 완료 기한이 필요하다면
시각 판단과 상태 전환을 같은 계약 아래 수행하는 주체가 필요하거나, 더 약한 규칙을
명시해야 합니다. 이 실험은 새 승인 주체나 해결책을 구현하지 않습니다. prepared
hook은 관측을 위한 장치이지, 운영용 승인 방법의 제안이 아닙니다.

선택 대상은 로컬 Git ref 하나이며 배포나 외부 작업이 아닙니다. 시계 오차, 비협조적인
작성자, 전원 차단, 인증된 승인에 대한 보장은 없습니다. 기존 다섯 사례와 승인 사용
기록 실험의 원본은 각각 당시 소스 리비전을 유지합니다.

Git 문서의 [prepared·committed 단계](https://git-scm.com/docs/githooks/2.53.0#_reference_transaction)와
[`update-ref`의 이전 값 조건](https://git-scm.com/docs/git-update-ref)을 근거로 삼습니다.
어느 쪽도 CAS에 애플리케이션의 만료 시각 조건을 추가하지 않습니다.
